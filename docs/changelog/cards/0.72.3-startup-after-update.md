# Start-up no longer takes 10-50 s after an update

**Branch:** t3/d22243b9   **Commit:** c314c46   **Size:** M
**Apps:** desktop (the cache code is in hopper-core, so Hopper Server gets the same fix; its start-up path was not timed)

## From -> to
- Before: the first start after every update opened every jar and parsed every config again before the window showed (10-50 s on real data). Later starts took 0.3 s.
- After: the caches survive an update. An update start costs about the same as any other start.

## Cause
- `stampcache.rs` threw its whole cache away when the Hopper version changed (`jar-ids.json`, `config-counts.json`).
- `modpack::claim_shipped_jars` runs in `instances::load`, on the way to the window, once per instance (`Store::new` -> `refresh` -> `discover`). For an instance with a pack override jar it reads the mod ids of every pack jar (`claim_override_jars`). With the cache gone that is thousands of jar opens.
- It also never ended: any mod the player added kept the check running on every start, and what it read was saved only when a record changed.

## What changed
- Each stamp cache has its own format number next to the code that makes the value (`deps::OWN_FORMAT`, `configindex::SUMMARY_FORMAT`, both 1). Bump it only when the parsing changes. Old files (they held a version string) read once as a different format and are rebuilt.
- `Instance::shipped_checked` (saved in `hopper.json`): the pack file already checked. Later starts skip the check. A pack update has another file id, so it is checked again. A pack with no known file list is not marked.
- The jars `claim_shipped_jars` reads are saved even when no record changed.
- `time::timed`: logs how long a step took (debug always, info over 0.5 s). Used on the start-up steps (`refresh`, instances, accounts, scheduler, per instance pack check and logos).

## Caches checked
- Version-keyed (fixed): `jar-ids.json`, `config-counts.json`.
- No version wipe, nothing to change: `scan-cache.json`, `peerhash.json`, `cfghash.json`, `mrsides2.json`, `mod-updates.json`, `source-cache.json` (keyed by file stamp or content hash only).

## Measurements (scratch data dir, throwaway instances only)
Scratch: 3 instances x 502 jars (3,000 entries each, ~870 MB), each a pack with one override jar and one player jar. "refresh" = `Store::refresh` in the log, the part before the tray icon. Window = process start to tray icon (about 3.4 s more than refresh: process start and this runner's polling).
| Run | Before (0.72.2 + timing logs) | After |
|---|---|---|
| First start, no cache | refresh 29.7 s, window 33 s | same (reads once, then saves) |
| First start after an update (old-format cache present) | refresh 25.8 s, window 29 s | refresh 28.9 s, window 32 s (once: old files are rebuilt, and the instances have no note yet) |
| Next start | refresh 23-24 s, window 27 s (every start: the read jars were never saved) | refresh 79 ms, window 3.5 s |
| Start after an update (cache from another app version, no note in `hopper.json`) | n/a | refresh 277 ms |
| Start with the note, no cache | n/a | refresh 75 ms |
All 25-30 s is "checking the pack's own jars" (10 s per instance); the log says so.
The runner's "window" figure includes about 3.4 s of process start; the app log alone shows started -> tray in 0.65 s for a warm start.
Not measured: real instances (not touched), a Hopper Server start, a second machine.

## Notes for the maintainer
- Not moved off the window path. The pack check changes instance records (`from_pack`, links, icons) that the first draw reads; running it later means rows change after the window shows, and `refresh` would need to hand the result back. With the cache kept and the note, the check costs about 0.3 s for 1,500 jars. If it should still move, it needs a "records changed" message to the store.
- The first start of THIS build is still slow once: the old files are rebuilt and instances have no note yet. The next start is fast.
- When you change how a jar's mod ids or a config's counts are read, bump `OWN_FORMAT` or `SUMMARY_FORMAT`, or players keep old answers.
- Left alone: `sources::looks::fill` opens the jars that need a logo or author on every start (in-memory memory only). It is cheap with a warm disk and was 9 s for 400 jars on a cold one (right after the scratch jars were written), so a first start after a reboot can still pause. It is not tied to updates.
- `scan-cache.json` and the hash caches have no format key; a change to what they hold needs a rename like `mrsides2`.
