## Why a separate field (not project_id = 282001 plus a "no updates" flag)
Many places read `project_id` to mean "this file belongs to that project": update checks and "Update all", the update/archived lists, share codes (`file_entry`), group-sync keys (`addon_key` = `p:<id>`), only-here, duplicate detection, the revert and backup paths, snapshots, `PackMods::Listed`, the hosting sync (`version_change`), the `packdiff` and `serverpack` checks. With `project_id` = 282001 the override row and the pack's own row would be one mod in all of them (a share code could publish 1.120.2 as the pack's 1.113.1), and each place would need its own "unless override jar" flag. A display-only field changes none of them; only the places that show a mod (icon, click, Unknown) read `shown_project()`. Cost: one more saved field (written only when set).

## Consumers checked (they keep reading `project_id`, which stays 0)
Update checks (`install::check_updates`, via the new tested `update_projects`; `modrinth_updates` needs `mr_sha1`, cleared; `sources::updates` needs `source`, none), "Update all", archived check, share codes (`sharecode::file_entry` none, `groupsync::addon_key` `n:<file>`, `onlyhere::mark_here` named target), duplicate detection (`install::duplicates`, same result with or without the field), version change / server sync (`ModFit` treats project 0 as "no match"), backups and revert (need project and file id), snapshots, `serverpack`, `packdiff`.
Desktop display: row icon and name click, requires/breaks links (`shown_project`), the peek icon map, Unknown filter, rail count and links-menu count.
Left alone on purpose: row menu "has project" (versions, open on site) stays off, so no version change is offered.
