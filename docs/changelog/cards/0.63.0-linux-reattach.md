# Hopper Server on Linux: running servers are picked up again after the panel restarts

**Branch:** t3/linux-reattach-running-servers   **Commit:** 1ecb60c   **Size:** M-L
**Apps:** Hopper Server (Linux). Desktop shares process.rs but is Windows-only; Windows behaviour unchanged.

## From -> to
- Before: after a Linux panel restart (update, crash, systemctl restart) running servers became orphans: no console, commands or stop. Linux self-update waited for every running server to stop.
- After: the restarted panel reconnects (console from the top, commands, stop, kill), like Windows. Updates go ahead with servers running; only servers started by an older panel (or without the FIFO) still trigger the wait / "Stop servers and update" flow.

## Notes for the maintainer
- Check Linux CI: the four unix tests, and that nothing else on Linux trips over the FIFO.
- FIFO lives in `<data>/run/<fnv64 of canonical server path>.stdin`, not the server folder (file browser/SFTP/backups would block on it and eat commands). Same data dir needed across restarts (the unit passes --data).
- Identity on reattach: /proc start time + /proc/<pid>/cwd == server folder + /proc/<pid>/fd/0 is the FIFO (the run file sits where users can edit files, so a pid alone isn't trusted).
- The unit already had KillMode=process since M6, so no reinstall note needed.
- The first update onto this version still waits (the running old panel decides); later ones don't.
- Servers already running from an older panel can't be adopted (no run file on Linux before); they need one stop/start.
