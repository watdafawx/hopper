# Mod icons and downloads no longer hang on connections the network drops

**Branch:** t3/5ccc7456   **Commit:** c52bf36   **Size:** M
**Apps:** both (shared `hopper-core` HTTP agents; Hopper Server uses the same download agent). Hopper Server not run.

## Root cause (outside Hopper, made worse by Hopper)
- Not IPv6: local DNS (192.168.50.3) gives no AAAA for cdn.modrinth.com, FOX has no v6 route; ureq 3.4.2 already walks every resolved address.
- Not UA / TLS / HTTP2 / format: Sodium's icon is a valid VP8L webp (4800 B); it was already in the real cache (`Hopper Data\cache\images\4bd3584e….webp` + `.still.png`, Nov 6).
- It is connection loss on the route to two Fastly addresses. curl, 2 s connect limit, 20 tries each:
  `151.101.1.242` 5/20 then 8/20 stalled, `151.101.193.242` 4/20 then 5/20, `.65.242` and `.129.242` 0/20; media.forgecdn.net, api.modrinth.com, github.com 0/20.
  Every resend of the first packet is lost, but a new connection (new local port) usually connects in ~70 ms. Windows resends for ~21 s (initial RTO 1 s, 4 SYN resends).
  Local DNS hands out one of the four addresses at a time (seen `.65` and `.193`), so it comes and goes; PowerShell "working" was likely a good address at the time.
- In Hopper (0.61.0 code, `imglog-before-failed.txt`): two Modrinth list icons `failed` after 21.1 s / 21.6 s. A failed image stays `Image::Failed` for the session, so it "never loads" until restart.

## From -> to
- Before: a lost connection waited the whole connect limit (10 s API, 30 s downloads, or Windows' 21 s) and failed.
- After: a connect with no answer in 2.5 s is dropped and a new connection opened (then 3, 4, 6 s, then the rest) inside the agent's limit.

## Measurements (live, pinned to the two lossy addresses, 40 fetches of Sodium's icon, 10 s connect limit)
| Agent | Failed | Worst |
|---|---|---|
| plain ureq (before) | 18/40, 11/40, 14/40 (three runs) | 10.0 s (fail) |
| retry, first try 3 s | 4/40 | 10.0 s |
| retry, first try 1.5 s | 0/40 | 3.7 s |
| retry, first try 2.5 s (shipped) | 2/40 | 10.0 s fail; ok ones 2.7–9.7 s |
2.5 s not 1.5 s: Windows takes 2.04 s to report a refused connect (measured), so 1.5 s would turn every refused host into a full-limit wait. The API agent's connect limit went 10 → 20 s so it gets 5 tries (downloads already 30 s).
