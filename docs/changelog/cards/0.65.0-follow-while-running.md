# Followed and group packs update while the game runs

**Branch:** t3/follow-sync-while-running (uncommitted, on top of bda1646)   **Commit:** none yet   **Size:** M
**Apps:** desktop only. Hopper Server has no follows or group copies.

## From -> to
- Before: while a friend played, their copy of a followed pack or a group pack got no changes. The friends row said "changes come when the game closes", and the changes only went in after they quit.
- After: changes go in while the game runs, the same way Update mods works. The Mods tab shows "Changed while the game runs: restart it to load the changes". A mod the game holds open is turned on or off once the game closes; the Mods tab says so ("1 mod the game has open will be turned off when it closes."), and nothing fails.

## How tested
- Tests: `cargo-test-changed.ps1`: hopper-core 1193 passed, including the new `locked::tests::locked_switch_waits_for_the_game` and `a_move_out_replaces_a_queued_switch`; hopper bin 79 passed. hopperd: `ui::tests::built_page_has_no_inline_script_or_style` fails because this worktree has no built web UI (`crates/hopperd/ui/dist` missing). hopperd wasn't changed.
- On screen: two scratch Hoppers (A, B) and a local relay (`relay/hopper_mailbox.py` on 127.0.0.1:8811), all with HOPPER_LOOPBACK=1. A made a throwaway Fabric 1.21.1 instance "FT" (Modrinth: AppleSkin, Mod Menu, Fabric API, Placeholder API), shared it with B, and B followed it into a new instance. A fake game ran on B: `java Hold.java <appleskin jar> --gameDir <B\FT>` opens the jar with `java.util.jar.JarFile`, and Windows then refused a rename ("being used by another process"). Hopper showed B as Running. A turned AppleSkin off and added Mouse Tweaks. Within about 15 s, B had Mouse Tweaks, the banner showed, and `.hopper-locked.json` held the AppleSkin rename. I stopped the fake game: the jar became `.jar.disabled`, hopper.json says `enabled: false`, the list file was gone, and the Mods tab shows it off.
- NOT checked: group packs kept both ways (same code path, `groupsync::apply` → `set_enabled_later`, not run live); a follow that updates the modpack version while playing; a real Minecraft launch; light theme.
- Test data: everything under the session scratchpad (`…\scratchpad\ft`). No real instances, no real relay, no hacks left in code.

## Notes for the maintainer
- Follow-up commit: the Mods tab's own switch, drag-pick sweeps, the menu's Enable/Disable and MCP `set_mods_enabled` also wait now (Store::set_enabled → `set_enabled_later`). The row switch shows the state it will end in (`Store::waiting_switches`, in the table fingerprint), so flipping it again cancels the waiting switch. Checked on screen afterwards (see "Manual switch with a held jar").
- Hopper Server: a server's java holds jars the same way. Its mods toggle and bulk toggle use `set_enabled_later`, and `LocalServer::start` flushes the queue before Java loads (this also fixes old jars from removals/updates while running, which were queued but never flushed on servers). The panel's switch keeps its old state until the restart; the panel already says "Restart the server to load them". No panel UI change.
- Asked in the session, not done: History has no "Added" entries (by design: it lists files set aside). Locks don't travel with follows or groups (not in share codes).
- The invite step ("Invite a friend") put a code on the system clipboard during testing.
