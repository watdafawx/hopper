## Findings / security behaviour
- M1 fixed: drop guards cap pre-auth tasks at accept time; integration reconnects 12 times with a half-open socket and held authenticated homes, control replies acknowledge completed takeovers.
- M3 fixed: /24 and /64 accounting; at most 192 first-ten-second direct streams, leaving part of 256-stream table free for players already authenticated by Velocity and control/voice streams during admission window. Actual mux refusal produces full-server wording for direct players.
- L1 fixed: missing Velocity refuses route before Login Start; home independently rejects non-Velocity streams for Relay records. Existing direct and Velocity backend paths preserved.
- L4 fixed: completed authenticated link removes IP failure queue.
- L8 fixed: prune expired entries at cap; evict oldest remaining entry before inserting a new IP, keeping at most 10,000 recent IP queues.
- L7 not done: shared absolute handshake/Login Start deadline needs deterministic deadline plumbing/tests beyond optional few-line scope. Existing ten-second per-read deadlines unchanged.
- SECURITY: network limits now aggregate players behind same /24 or /64; auth/roles/setup/TLS/path rules unchanged. Failure-map eviction drops oldest queue under saturation. No wire changes; old home/relay formats unchanged.
- Capacity reserve uses review's simple ten-second approximation, not Minecraft Login Success parsing. Long-lived stalled logins can still fill total mux capacity after ten seconds; capacity is not an absolute botnet guarantee. Four simultaneous unauthenticated sockets from the same home IP can still exclude another until one ends; one lingering socket does not prevent legitimate reconnects.
