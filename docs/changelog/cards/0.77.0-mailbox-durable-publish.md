# Friends sync: a change sent just before a mailbox crash is no longer lost

**Branch:** t3/mailbox-durable-publish-before-ack   **Commit:** 58dbc5e   **Size:** S
**Apps:** the mailbox relay only (`relay/hopper_mailbox.py`). No desktop or Hopper Server code changed; Hopper Server has no friends sync.

## From -> to
- Before: the mailbox answered a publish, saved ~1.5 s later. A crash in between lost it, the desktop had already counted it as sent, and it was never sent again (gap 3 of the sync-scenarios card).
- After: every change is in the state file (temp file, fsync, atomic rename) before the 2xx answer. A failed save answers `503 save_failed`, so the desktop keeps the change and sends it again.

## Which routes save before answering
Every POST that answers below 400 (the answer waits for `flush()`):
- `/v1/recipes` (pack publish: direct, group, old one-friend form) and `/v1/revoke` (unshare/delete): the ones a desktop treats as delivered (`mailbox_sent`, group copy `seq`/marks).
- `/v1/join` (friend made, invite code used up), `/v1/invite`, `/v1/remove` (unfriend), `/v1/profile`.
- `/v1/groups` (create), `/v1/groups/<id>` (edit), and `/delete`, `/accept`, `/leave`, `/in-step`, `/follow`.
- `/v1/register` already saved first (unchanged).
- Not saved per request (still the 1.5 s saver): idle account clean-up, event expiry, `last_seen`.

Also new: a long-poll only hands out events that are in the file (`visible_seq`), and its `seq` is the newest saved one. Without it, B could hear of an event, the mailbox crash, and A's retry would get a lower seq than B already holds: B would skip it.

## Idempotency: answer lost after the mailbox saved
The desktop sees an error and keeps the change as unsent (`out.failed`, `src/gpui/store/friends.rs` ~2243; `note_sent` only on Ok), so it publishes again later.
- Publish / revoke: safe. A new recipe replaces the old one for the same sender and pack (`same_event`), so the queue doesn't grow; the group pack is overwritten in place. The receiver gets the same code again with a higher seq (a no-op apply, and their cursor moves on). Cost: one extra event and a changed `at`.
- Not idempotent (unchanged by this fix, all rare): `join` retry gets 404 `invite_unknown` though the friendship exists (code was consumed); `create group` retry makes a second group with the same name; `edit`/`accept`/`leave`/`follow`/`in-step` are safe to repeat.

## Notes for the maintainer
- **State format: unchanged.** No migration. New server reads the old file, old server reads the new file. Rollback = put the old `hopper_mailbox.py` back.
- Deploy steps (when you choose to; I did none): 1. `sudo systemctl stop hopper-mailbox` 2. `sudo cp -a /var/lib/hopper-mailbox/state.json /var/lib/hopper-mailbox/state.json.pre-durable` 3. copy `relay/hopper_mailbox.py` to `/opt/hopper-mailbox/` 4. `sudo systemctl start hopper-mailbox`, check `journalctl -u hopper-mailbox` shows no `state save failed`. The unit file needs no change (state dir already writable; the `.tmp` file sits beside it).
- Desktop text: `save_failed` has no entry in `mailbox::says_code` (`mailbox.rs`, not mine), so players get the generic message on that rare 503. Worth adding "the sync service couldn't save that, we'll try again" there.
- On a save failure the change stays in memory (hidden from feeds) and the saver retries; the desktop's retry replaces it. Joins/group creates in that window are the non-idempotent ones above.
- Every change rewrites the whole file. At the 24 MB limit that is ~65 ms per publish, requests together share a write. If the file ever grows past that regularly, the next step is an append-only journal; not needed now.
