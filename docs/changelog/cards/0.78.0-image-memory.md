# Hopper no longer holds on to every description picture and GIF

**Branch:** t3/desktop-image-atlas-memory-leak   **Commit:** ddf9f7ab   **Size:** M (diagnosis was L)
**Apps:** desktop only. Hopper Server's web UI leaves images to the browser, so it has no such cache.

## From -> to
- Before: every picture and GIF frame from a description page stayed in memory, on the CPU and the GPU, until Hopper quit. Memory went up with every page and never came back down.
- After: description pictures share the picture cache's 96 MB budget and are freed when it trims. GIFs are limited by size as well as count, and a GIF no page has drawn for 20 s is freed (a page that shows it again decodes it again).

## Root cause
1. `widgets::description_view` gave markdown pictures to GPUI as `Resource::Path`. GPUI's asset cache never evicts, so each picture stayed decoded at full size, and its atlas tile was never removed. A picture 1024 px or bigger gets its own D3D texture: these are the maintainer's 8,294,400 (1920x1080), 15,728,640 (2560x1536) and 7,864,320 (1920x1024) blocks.
2. Decoded GIF clips (`store.rs`) were bounded only by count: 12 page clips of up to 48 MB each and 40 logos of up to 16 MB each. A kept clip holds every frame twice once drawn (CPU pixels plus GPU atlas tiles).
3. The GPU atlas only frees a 1024x1024 texture (4 MiB) when every tile in it is gone. The NVIDIA driver commits zeroed system memory for each texture, so each one also shows up as a standalone 4,194,304-byte private block. The "139 identical buffers" were these all-zero driver blocks, not 139 copies of one picture. Reading them with ReadProcessMemory faults them into the working set, so the scan itself inflates the WS figure.

## Measurements (release builds, rig, scratch data, same script)
Repro: 30 CurseForge project pages (`navigate {"project":id}`, scrolling each description), then 30 pages from 5 GIF-heavy searches (animation, particles, create addon, physics, shader; first 6 cards each), then 60 s idle. Base = HEAD~1 plus the MCP `project` hook only.

## Notes for the maintainer
- Left over: 20 atlas textures at idle, mostly the picture cache's GPU copies (Browse logos at 224 px: 56 px x 2 scale x 2 headroom), bounded by its 96 MB budget. To get "only what's on screen" on the GPU, thumbs would need to drop GPU copies of pictures not drawn for a while. That is risky with cached GPUI views (a reused scene can point at a freed tile), so I didn't do it.
- `Store::forget_images` (Settings > clear image cache) clears `anims` without freeing the clips' GPU copies. It's a small leak, rarely hit, and I didn't fix it.
- Pictures of 1024 px or more each still get their own D3D texture while in the cache; that is GPUI's atlas design.
- GPUI wasn't patched. The atlas probe was a temporary local copy only.
