# Friends: see which changes are still waiting to be sent, and why a send failed

**Branch:** t3/offline-sync-waiting-status   **Commit:** e97b085   **Size:** M
**Apps:** desktop only (Hopper Server has no friends/group sync)

**Mock:** https://claude.ai/artifact/CnAUeBD4WMGUHEidHyZidL. Pick: A, a count on the Friends icon plus a line in the panel. It reuses the measured History count badge, shows on every page, and the line says what happens next. B's new top-bar chip crowds the bar when a side panel is open.

## From -> to
- Before: a change made offline, or one the sync service refused, vanished silently. Nothing told the player it hadn't reached the group, and "storage full" said only "something went wrong". Members never saw the names of the sharer's hand-added jars. The Follow dialog said "your copy updates when X changes theirs" even for group packs, where changes go both ways.
- After:
  - Waiting changes show as a count on the Friends icon plus one line in the Friends panel: "waiting to be sent… go out by themselves when Hopper can connect again", "Sending your changes to X…", or "Hopper tries again in a minute". The count clears once the send goes through.
  - A refused send shows a notice once, with a reason that says what to do.
  - Members see the hand-added jars by name ("X isn't on any mod site… Ask Ada to send it").
  - The Follow wording is two-way for group packs and one-way for a direct share.

## Notes for the maintainer
- **Baseline:** the first look at each shared pack after launch counts as already sent. A change made while Hopper was closed, or one that failed just before quitting, isn't counted after a restart.
- **Re-sending an old state:** going back to a mod list that was already sent doesn't show the count, because nothing new needs to go out. That's correct, but it surprised me while testing.
- **A sharer's untracked jars:** a jar that's only in the mods folder (shown as "1 jars not from CurseForge") wasn't in the sharer's `left_out`. Members saw it by name only with a `left_out` sent by hand. That gap is in the share code (groupsync/share), which this session doesn't own. Worth a look.
- **Unreachable sends** stay out of the notice on purpose: the "Can't connect" bar already covers them.
- **Seen, unrelated:** "POST /v1/mods: http status: 404" on the Mods tab. The fake CurseForge ids in the scratch pack cause it.
