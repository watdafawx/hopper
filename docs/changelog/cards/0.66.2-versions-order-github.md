# Versions dialog: GitHub, link and Modrinth mods get the right Update / Roll back buttons

**Branch:** t3/6cda1a7e   **Commit:** 1792d57   **Size:** M
**Apps:** both (desktop and Hopper Server share the new `hopper_core::file_age`; the web UI view needed no change, the server sends `older` / `behind` / `latest`)

## From -> to
- Before: for foxs-tweaks (GitHub) with the newest v1.23.1 installed the dialog said "4 versions behind · Update to v1.20.0"; older rows mixed "Update to" and "Roll back to" at random. File ids were compared, and a GitHub / link / Modrinth file id is a hash.
- After: newest installed shows "Up to date" and every other row "Roll back to". Installed v1.20.0 shows "6 versions behind · Update to 1.23.1"; v1.20.1 to v1.23.0 say "Update", v1.19.0 and older say "Roll back".

## How it orders
Both CurseForge: file id. Otherwise release version when both tags read as versions ("v1.23.1"), else publish date (minute, then seconds). A link's ETag or a branch commit is never read as a version. The release tag beats the date because a re-uploaded asset moves its date. Missing data counts as the same age (no offer, no "behind").

## Notes for the maintainer
- `store::note_update` (stale CurseForge cache fix) now only runs for mods whose ids order (CurseForge); GitHub / link mods already get offers from their source.
- In a server pack dialog and pack Versions with a Modrinth or link pack, the installed file is known only by id when not in the list, so the "update" offer is kept as the source gave it (no re-filter).
- `install.rs` list sort by `file_id` (mod table order) left alone: display only.
- Mixed version / date orders are not a strict total order, so `file_age` has no sort helper; it only answers "is this newer" and "which is newest".
