# Friend groups: catch up after being away, pack mods turn off, old versions stay gone

**Branch:** t3/group-offline-sync-catchup   **Commit:** 0c1c660   **Size:** M (logic only, no UI change)
**Apps:** desktop + relay (Hopper Server has no group sync)

## From -> to
- Before: a member who was offline missed the other members' changes; a pack mod the sharer turned off stayed on for members (the task still said "changed"); a member passing a change on late brought older mod versions back (ATM10: crazyphone, vista, botany via another member's copy).
- After: a member who comes back gets every change, in one batch per sender; pack mods turn off/on/out for everyone; a late copy can't undo a newer change.

## Causes
1. **Copy dropped at start** (`groupsync::reconcile`): a group pack followed by hand has `FollowedRecipe.group == ""`; the group came only from the feed, which is empty for the first 500 ms after starting. The first publish tick dropped the copy (and revoked it on the relay), then rebuilt it with only the sharer's code, so other members' next codes counted as a starting point (hypothesis 1) and their changes were never made.
2. **Follow code set before the merge** (`friends.rs got_recipe`, hypothesis 3): a restart between arrival and merge skipped the changes. Now set when the merge takes the code (`on_group_merged`).
3. **Pack mods named by file** (bug 2): Modrinth-pack and sha1-matched mods have key `n:<file>`, but `apply` looked mods up by `p:<project>`: silent no-op, notice shown anyway. Now `find_addon`; `does_something` drops changes that do nothing from the task; a locked jar notes "turns off when the game closes". `onlyhere::split` matches file-named keys too.
4. **Late pass-on reverts** (bug 3): a behind member's copy republished an old change; receivers dated it with the carrier's newer event number, so it beat the newer change. Now each mod's state carries a stamp `{seq, by}` of the change that made it (new optional relay field `marks`); a stamped change no newer than what's known is Older.
5. **Held change overwritten** (hypothesis 4): after `HELD_FOR`, `ignore_unsent` let others' changes overwrite the local unsent one. Now `give_up_held`: local change wins, theirs to that mod dropped.
6. **Relay reset**: `relay_reset()` zeroes copy numbers when the mailbox starts over, else everything looked Older.
- Not causes: hypothesis 2 (strays fine once copies persist), 5 (`fresh` doesn't gate copies), locked jar (the game wasn't running; kept as a regression test).
