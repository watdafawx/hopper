# Pack/update labels: the header, Update all and the task title count and name the same things

**Branch:** t3/f4dc29c5   **Commit:** 5aa8598c   **Size:** M
**Apps:** desktop for the counts and the task title. Hopper Server has no Update all button or update task title (its mods view lists and enables files, no update flow), so there is nothing to match there. Bug 3 (peek "Installed") is **not fixed**: it needs `src/gpui/browse.rs`, which another agent owns this batch (see "Not done").

## From -> to
- Header vs Update all (bug 1): before, the header pill and the pack-tab suffix counted **projects** (`update_list::counts`, one per project id) while the toolbar counted the offers it held. Two files of one pack, or one project with two copies, could make the two numbers differ. After, both count the **rows the player sees**: mods once per project (an old copy folded into the row is not a second update), resource packs, shaders and data packs once per file/copy. `pending_rows()` in `hopper-core` is the one function all three use.
- Task title (bug 2): before `Updating mods in <instance>` for everything, even a resource pack, shader or data pack update. After the kinds of the updates being run:
  - all one kind: `Updating mods in <instance>` / `Updating resource packs in <instance>` / `Updating shaders in <instance>` / `Updating data packs in <instance>`
  - a mix: `Updating 1 mod, 2 resource packs in <instance>` (tab order, plural only above one)
  - an update that names nothing installed: `Updating content in <instance>` (was "mods", a guess)
  The title still truncates its tail in a narrow tasks list (the instance name goes first); a hover tooltip now carries the whole title.
- Peek "Installed" mark (bug 3): **not changed**, needs `src/gpui/browse.rs`.

## Not done / found on the side
- **Bug 3 (peek "Installed") not fixed.** The mark is in `src/gpui/browse.rs`: the peek (`BrowseView::peek`) stores only `target` (instance) and the selected project, and `installed`/`installed_file` take the first addon with that project id (`installed_as` -> `hopper::browse::installed_addon`). The fix needs `browse.rs` to carry the copy that opened the peek (the row's file name or where-key) and to look the addon up by it (row key), plus a test; `browse.rs` is owned by another agent this batch, so I left it alone.
- The core `still_applies`/`keep_current` still collapse two offers of one project to the first addon's file name, so a hand-seeded list cannot show two surviving offers for one pack; the counting rule is unit-tested instead. Two live Modrinth copies (two hashes, same project) produce two offers and now both count, which is the path that made the header and Update all disagree.
- shaders and data packs were not run on screen (same `pending_rows`/`kinds_label` path, unit-tested); only Hopper Dark and Hopper Light; no narrow-window shot of the title.
- Existing quirk seen while testing (not touched): the update list keeps one offer per project, and `still_applies` rewrites a second copy's offer to the first copy's file name.
