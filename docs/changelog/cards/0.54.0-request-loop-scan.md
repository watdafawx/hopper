# Hopper Server: pages no longer ask the panel for the same thing every second

**Branch:** claude/request-loop-scan-3f333d   **Commit:** c6eacff   **Size:** M
**Apps:** Hopper Server web UI (+ panel log line), desktop (one small fix; rest reported only)
(Card is in the worktree: a hook blocks writing to the main checkout's .claude from a worktree.)

## From -> to
- Before: opening any server page made the browser ask for `/servers/<id>/crash` every second (and Worlds, Data packs, Settings > Sleep did the same for their own endpoint). Nothing stopped a page that looped; the panel's rate limit did, after ~1,200 requests.
- After: those pages load once and again only when something really changed. The api wrapper refuses a looping GET before it is sent, a build check flags the pattern, and the panel logs a warning at 80% of its limit.

## Root cause (a second one, beyond Sleep's own loop)
The live feed replaces every `server` object each second. Any `$effect` that reads `server.id` / `server.state` directly re-runs every second. The old comment in Sleep.svelte already said so, but 8 components still did it. Measured before the fix (idle, one server page open):
| Page | Requests/min | The repeating one |
|---|---|---|
| every server tab (Console ... Schedule, all Settings pages) | 110-125 | `GET /servers/alpha/crash` x ~12 per 12 s (CrashStrip) |
| Worlds | 160 | + `GET /servers/alpha/worlds` 1/s |
| Data packs | 175 | + `GET /servers/alpha/datapacks` 1/s |
| Settings > General (Sleep) | 180 | + `GET /servers/alpha/address` 1/s (the master's fix still reloaded each second) |
| old Sleep.svelte (before the master's fix), scratch panel | ~2,900 | `GET /servers/alpha/address` 711 in 15 s, 25 x 429 |

## Guards
1. **Brake** `src/lib/brake.js` + `api.js`: identical GETs in flight share one request (clone of the data per caller); more than 10 identical GETs in 5 s are refused in the browser with a console `request loop?: GET <url> x N in 5 s`; one toast `This page is asking too often, paused it` after 30 in 10 s; `api(path, { poll: true })` opts out (job progress polls at 500-600 ms). The live feed is a WebSocket, not `api()`.
2. **Loop check** `scripts/check-effects.mjs`, run by `pnpm build` and `pnpm check` (docs in `crates/hopperd/ui/README.md`). Flags `loop` (reads `$state` it assigns after an await), `key` (fetch-named call with no untrack and nothing read), `prop` (reads `server.x` directly). Escape: `// loop-safe: <reason>`. Cleared: 3 annotated with real reasons, the rest fixed. Fixtures in `tests/fixtures/`.
3. **Panel log** `security.rs`: one warning per address per minute at 80% of 1,200 (960), three busiest paths, paths only. Limits unchanged.

## Proof for the Sleep loop (scratch panel 127.0.0.1:48110; old Sleep.svelte from d51a298~1 in a scratch Vite copy)
- (i) Old code, no brake: 711 `GET /servers/alpha/address` in 15 s (~2,900 req/min total), 25 answers `429`. Panel log then: `127.0.0.1: 960 requests in under a minute (limit 1200); busiest: /api/v1/servers/alpha/address x897, /api/v1/pair/pending x18, /api/v1/jobs x11. A page may be asking in a loop.`
- (ii) Old Sleep + new api.js: 13 address requests in 15 s, console `request loop?: GET /servers/alpha/address x 11 in 5 s`, the page stopped.
- (iii) Lint on old Sleep.svelte: `[loop] $effect reads $state info and assigns it after an await/callback` (+ `[prop]` for `server.state`). Current code: `check-effects: ok`.
- Current code: ticked "Sleep when empty", still ticked after 8 s, 0 address reloads, idle ~50 req/min.

## Desktop (src/gpui): read-only audit by a subagent; one fix
No hot loop. One desktop, one panel, 10 servers, idle: ~165 req/min (console closed), ~315 with the console open. Main sources: `panel_poll` (store.rs:846) every 5 s = 4 requests per panel (`/servers`, `/host`, `/alerts`, `/hello`; 48/min per panel; no pause when minimized; same pace after an error or 429); per-server `ServerControl` poll (3 requests every 1-2 s, 4/s with the console open).
- FIXED: `ServersView::hidden()` never slowed the control's poll, so after leaving the Servers page it kept polling every 2 s (1 s with the console tab) until the app closed. `hidden()` now calls `set_active(false)` + `set_console_open(false)`, `shown()` restores them (`servers.rs`). Compiles (`cargo check --bin hopper`); NOT run on screen.
- NOT fixed, master to decide: `panel_poll` has no backoff on error/429 and runs minimized; `/hello` + `/host` could be cached ~60 s (4 -> 2 per tick); hopper-core client has no 429 handling; four idle desktops on one address ~660/min. Unverified: whether `pre_join_key` (join_help.rs) changes every poll (then 2 requests per paired pack every 5 s).
- No request counter in the desktop; sync-timing.log only records Sync-tab compares.

## Rate limits (review)
1,200/min per address and 20/min for sign-in/setup/pairing: unchanged. An idle panel page is now ~40-70/min. A loop is cut by the brake (~120/min) long before the limit and logged at 960.
