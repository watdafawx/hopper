# Count badges: digits centred at every zoom

**Branch:** claude/badge-zoom-4743f6   **Commit:** a7ebf0a   **Size:** S-M
**Apps:** desktop (Updates icon on the Mods rail + History button, now one shared badge) and Hopper Server web UI (`.bdg`, History button)

## From -> to
- Before: at the user's 125 % zoom the digits of the Updates badge sat 1 px from the top and 3 px from the bottom of the pill (the user's screenshot and my reproduction agree to the pixel). At 175 / 200 % the 14 px pill was no taller than its digits, which overflowed.
- After: the pill is sized from the rem (as the digits are), painted on whole pixels, and the digits are placed from the font's cap height. Top and bottom gap match (0 px apart; 1 px at 67-80 %) at every zoom 67-200 %, for the rail badge and the History badge, in 3 themes. Web: within 1 px at page zoom 100-200 %.

## Root cause
Zoom scales rem sizes (`text_xs` = 0.75 rem) but the badge box was fixed `px()` (14 px high, 4 px padding, 3 px bottom nudge, anchor offsets, `rail_badge_extra`). At 125 % the digits are 10 px tall in a 14 px pill with a nudge tuned for 8 px digits. Both earlier "centred" claims were measured at 100 %. Second cause, found while fixing: even with a rem-sized box a flex-centred label lands 1 px high or low depending on the zoom and on the fractional pixel its parents sit on (the rail and History badges disagreed by 1-2 px at the same zoom), so the badge is now painted by hand.

## How tested
- Tests: `cargo-test-changed` 64 passed (new `badge_is_whole_pixels_with_a_balanced_gap_at_every_zoom`; `rail_badge_makes_room_as_digits_grow` per zoom).
- On screen: test exe `hv-badgezoom.exe`, MCP port 47844, scratch `HOPPER_DATA_DIR` (zoom, theme, window 2200x1300 set per run), throwaway 3-jar instance; counts faked through a temporary file read in `rail_view` and `HistoryButton::render` (not committed; no `TEMP-HACK` left). Each state needed a fresh process (cached views keep the first render).
- NOT checked: the live hopperd Svelte app (same CSS/markup measured on a static page in headless Chrome, device scale = page zoom); Firefox/Safari (no `text-box-trim`: they keep the old line-box centring); real instances; screens whose scale factor is not 1.0 (pill snaps to physical pixels, not exercised); History "99" (2 digits) in the batch and History at 110 % (my detector failed there; an earlier single run showed "11" at 110 % T3 / B3).
- Horizontal: digits are centred by advance width, so a leading "1" or a "+" can leave 2 px difference left/right (200 %: "11" 8/10, 12345 8/6, "99+" 5/7). Not changed.
