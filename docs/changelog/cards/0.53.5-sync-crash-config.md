# Sync tab: the mod list shows at once; the crash check comes after and is 3x cheaper

**Branch:** claude/sync-crash-config-177b52   **Commit:** bb76e7f   **Size:** S-M
**Apps:** desktop (the web UI's Sync page fetches `/crash` on its own, so nothing waited there; it gains the faster crash read once Hopper Server is rebuilt, because hopperd runs the same `crashdetect::server`)

(Card is in the worktree's `.claude/changes/sync-crash-config/`: a hook blocks writing to the main checkout from a worktree.)

## From -> to
- Before: Sync waited ~1 s on "crash and config reads" (the last crash plus its configs) before showing anything.
- After: the list shows as soon as the comparison is ready (14-21 ms on the fixture); the crash read runs beside it and fills in later (spinner on the server row). The crash read itself is ~3x cheaper.

## Root cause
`crashdetect::server` -> `switches()` -> `crashconfig::files_of` and `modconfig::files_for` list `config/` and call `path.is_dir()` / `path.is_file()` per entry (a stat each), once per blamed mod, twice per mod. On a `config/` of 3,000 entries that was ~590 ms of the 850 ms; `config_differs` repeated it (143 ms). Nothing hashes or diffs a config tree: only the crash's blamed mods' files (<= 8 per mod) are read. The rest of the crash analysis (jar ids 55 ms, analyze ~190 ms) stays, now off the critical path.

## Numbers (generated fixture: 1,157 jars, 3,000 config files, 41 crash reports, 766 KB log; `--profile local`)
| Stage | Before | After |
|---|---|---|
| `last_crash` cold | 1,105 ms | ~380 ms (GUI, fast profile) |

| Click to list shown | waited for the slowest read (~1,000 ms) | 14-21 ms (fixture; real comparison ~120-200 ms) |
