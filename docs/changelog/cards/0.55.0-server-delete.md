# Deleting a server no longer fails on a held folder, and you can delete for good (one checkbox)

**Branch:** claude/server-delete-232424   **Commit:** e7cae0d + follow-up (checkbox instead of typed name; see git log)   **Size:** M
**Apps:** Hopper Server (web UI + panel) and desktop (dialog + local/remote delete). The desktop part compiles but was NOT run on screen.
(Written in the worktree: a hook blocks writing to the main checkout's `.claude/changes` from a worktree. Screenshots are in both places.)

## Root cause
Hopper Server's own change watcher (`crates/hopperd/src/changes.rs`) watches every server folder (the folder itself plus mods/config/...). On Windows a watched directory (ReadDirectoryChangesW handle) can't be renamed: "Access is denied (os error 5)". The old code did one `rename` and gave up. Other holders (a scanner, Explorer, a program with a file open) hit the same wall. The original failure was not reproduced on rig (not touched); the named-holder case was reproduced in scratch with a helper process.

## What holds handles, how they are released
- The only long-lived holder in hopperd is the change watcher. New `Changes::release(root)` tells its thread to unwatch that folder and everything under it and waits (max 2 s) for the ack; `resume(root)` watches again if the move fails. Called before every try of the move.
- Checked, not holders: log/console readers and mod/crash scans read per request; no server child process runs (delete needs it stopped). `disk_watch` is desktop-only and watches instance folders, not servers.
- Restore/clone/rename have the same trap in principle; NOT changed here (restore moves out of `.hopper-deleted`, which the watcher does not watch).

## Retry + who holds it
`crates/hopper-core/src/hosting/fsmove.rs` (shared by both apps): rename retried 6 times over about 3.1 s on error 5/32, releasing handles each time. Still locked: the Windows Restart Manager (`RmRegisterResources` over the folder's files in chunks of 400, `RmGetList`) names the program:
`Couldn't move del-b: PowerShell 7 (pid 90384) is using files in it. Close it and try again. Nothing was changed.`
Nobody found: `Couldn't move X: something has the folder open (a folder is held, so no program can be named). Close Explorer windows and anything watching it, then try again. Nothing was changed.` Off Windows there is no holder lookup.
All or nothing: the folder is moved FIRST, then the worlds are kept out of the moved folder (`worlds::keep_worlds_to`; the old order moved worlds first and stranded them if the move failed). If keeping or writing the note fails, the folder is renamed back and worlds already moved go back (`worlds::unkeep`). If even that fails the error says where everything is. Never an in-place delete as a fallback.

## Permanent delete (web; `permanent: true` in the remove body, default false)
- Owner only (`require_owner`), server stopped, must be in the servers folder (same `in_root` check), no typing: the checkbox in the dialog is the deliberate step (changed from a typed name at the user's request: names with foreign letters or symbols are no fun to copy). The old `confirm` field is ignored.
- `permanent_target`: canonical path must be a direct child of the servers folder, not the folder itself, not a drive root, not a symlink/junction, not a `.hopper-*` folder.
- Renamed first to `.hopper-deleting-<time>-<name>` (same release + retry + holder naming, so a held folder fails before anything is removed), then the tree is removed (read-only flags cleared, 4 tries). If removal partly fails the error says what is left; `.hopper-deleting-*` is swept at the next panel start (logged).
- "Keep the world" works: worlds go to Kept worlds first. Log line: `deleted permanently (can't be undone)`; the request is in the audit log as usual. Not in History: it cannot be undone, and the dialog says so.
- Setting: Settings > Panel folder > "When deleting a server" (Move for 30 days (default) / Delete permanently) sets which choice the dialog starts on (`delete_permanently` in the panel config, `PUT /api/v1/settings/delete-default`, owner only). The dialog's "Delete permanently (can't be undone)" checkbox starts ticked when that setting is on; the user can untick it for one delete.

## Desktop
- Same checkbox "Delete permanently (can't be undone)" beside "Keep the world", no typing; ticked: line "The folder is deleted for good and can't be restored." and the danger button says "Delete permanently" (else "Delete server"). Not run on screen.
- Local server: worlds are no longer stranded if the Recycle Bin move fails (put back); a holder is named. Permanent: renamed to `.hopper-deleting-*`, then removed. Remote: sends `permanent` (and the name, for older panels that still want it typed); an older panel ignores it and moves the server (the job note says so).
- NOT done: the desktop does not read its `delete_permanently` setting (that one is for instances, default ON) for servers; servers start on the safe choice to match the web default. Your call.

- On screen (scratch panel, throwaway servers, loopback): default move + restore list; held file -> toast names PowerShell, folder untouched; released during the retry window -> delete OK after 2.4 s; checkbox on + keep world (101 files kept in Kept worlds, rest gone; log says deleted permanently); earlier build: permanent without keep, folder gone; permanent while held -> refused, 403 files intact; leftover `.hopper-deleting-*` swept at start (read-only file inside); the setting changing the dialog's start was seen with the earlier (segmented) build and not re-checked with the checkbox.
- NOT checked: rig, Linux/macOS, Docker, the desktop dialog on screen, a non-owner being refused (`require_owner` unchanged), the exact original failure.
- Test data: scratch servers and folders deleted afterwards; `%APPDATA%\hopperd` untouched (data dated 10/30).
