# Updates never swap a 1.21 mod for a jar made for Minecraft 26.x

**Branch:** t3/4fcd492e   **Commit:** 9d4c6faf   **Size:** S/M
**Apps:** both (shared hopper-core; Hopper Server's mods updates, installs and deps use the same calls)

## From -> to
- Before: "Update all" on a 1.21.1 NeoForge instance replaced Structory: Towers v1.0.15 with `Structory_Towers_26.2_v1.0.17.jar` (built for Minecraft 26.2), which NeoForge 21.1 rejects ("no modLoader").
- After: a mod jar that lists any year-named version (26.1, 26.2...) doesn't count as made for a 1.x instance. Updates, installs and "fits this instance" pick the newest file that really fits (v1.0.15 here). On a 26.x instance the same jar still fits.

## Root cause (real CurseForge data, project 'structory-towers')
- v1.0.17 `Structory_Towers_26.2_v1.0.17.jar` is tagged 1.21, 1.21.1 ... 1.21.11 AND 26.1, 26.1.1, 26.1.2, 26.2.
- v1.0.16 `..._26.1_v1.0.16.jar` tagged all 1.21.x + 26.1. v1.0.15 `..._1.21.x_v1.0.15.jar` tagged 1.21.x only.
- CurseForge's `latestFilesIndexes` lists file 8396885 (the 26.2 jar) as newest for 1.21.1 / NeoForge, and `gameVersion=1.21.1` file queries return it first. Hopper matched the tag exactly, so it was "correct" by tags; the author's tags are wrong.

## Notes for the maintainer
- An instance already on the 26.2 jar is not offered a "downgrade" to v1.0.15 (updates only go up). The user's real instance needs the file swapped by hand (Versions -> v1.0.15), or a follow-up: offer "the newest file that fits" when the installed one is wrong-era.
- Only .jar files are held back; resource packs / shaders tagged for both still fit (they often work across).
- Places now on the one rule: Update all / single update / update list (check_updates + modrinth_updates), install from Browse and dependency installs (best_file/pick_best), desktop Versions "fits this instance" (`File::fits`, browse.rs), every `source::files(id, mc, ..)` caller (revert, undo, version-change, instance_ops, mcp_data, hopperd mods_table / mods_more / parity_browse).
