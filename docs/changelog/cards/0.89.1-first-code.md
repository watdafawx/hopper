# Group sync: what a friend changed before their first share now reaches you

**Branch:** t3/first-code-group-sync-additions   **Commit:** 806a6e02 (released in 0.89.1)   **Size:** M
**Apps:** desktop only (group sync lives in hopper-core and the desktop store; Hopper Server has no group copies). No Hopper Server release this time.

## From -> to
- Before: a friend who joined a group and added, updated or switched a mod before their first share got out sent a code with no stamps for those mods. Every other PC took only stamped mods from a member's first code, so those changes reached nobody and every PC said "Same as the group".
- After: on a member's first code, a mod the code lists that your copy lacks, has as another file, or has switched the other way is made on your PC and shown as that member's change ("Added by Mia"). A mod the code does not list is still never removed.

## What was silent
- Only stamped mods were read from a member's first code (`groupsync::plan`, first-code branch).
- The sender has no stamps the first time: `sent_marks` returns nothing while `copy.sent` is empty, `mark_own` needs a previous code, `stamps_out` 0-stamps only against `sent`.
- No note, no log line, no status. Audit mode 4 (`.claude/review/friends-sync-audit.md`).

## What is taken now (`groupsync::first_changes`, next to `baseline`)
From a member's first code, besides its stamped mods (unchanged):
- a mod it lists that this copy lacks: added;
- a mod it lists as another file: that file;
- a mod it lists switched the other way, or a pack mod it turns off: switched.
Each is dated by the code's number and marked as that member's, the same as a later code's unstamped change.

Not taken (on purpose):
- a mod the code does not list, and a pack mod it takes out: a removal still needs a stamp;
- a mod the group dated a change of (a mark on this PC, or a stamp in any member's code): the member may only be behind, and dated by their code the old state would win and spread;
- a mod another member's taken code has that same way: that is how the group had it, so it is this copy that differs (a change made here);
- anything unstamped from a code of another pack version;
- locks, the loader, the pack version (they keep their own rules).

The last three guards are more than the brief asked for. Without the first one a member who is behind undoes a group update (a test proves it). Without the second a joiner's first code reverts another member's own update, and undoes a removal the joining member made themselves (a test proves it).

## First code with a failed lookup (0.88.4 rule)
- Before: a first code was kept whole as "taken", so a file that could not be looked up never came in.
- After: the file is cut out of the code kept, and the code is kept with `Got::partial = true`. The next read (start, Check now, their next share) treats it as a first code again, with the same guards. Without `partial` the re-read would compare with the cut code and take the file as a change the member made, which can bring an old file back (a test proves it).
- New field `partial` on `Got` (settings `group_copies`), written only when true. An older Hopper ignores it.

## Notes for the maintainer
- A removal made before the first share still reaches nobody (by design here: additions only). In the sim scenario the joiner ends without mod 4 and the others keep it. The 0.89.0 check lists it on the joiner's PC as missing.
- A mod the group already changed: the joiner's own version of it from before their first share is not taken, because it can't be told from being behind.
- Changes lost before this fix don't come back by themselves for PCs that already took that member's first code. A member who joins later should take them (their copy has no code from that member yet) and pass them on with a stamp; that follows from the rule but has no test.
- A copy with no marks and no taken codes at all (a sharer who unshared and shared again) has nothing to tell "behind" from "changed" by. The first member code read there is taken as that member's changes. Not tested.
- A first code whose file is gone from the site for good stays `partial`: that member's later codes are read as first codes on this PC (their own changes still arrive, since they carry stamps; an unstamped removal from an old Hopper would not).
- `groupverify::want_of` (0.89.0) picks the newest code that lists a mod when there is no mark, with no "behind" guard. Whether it can offer a behind member's older file as the group's was not tested.
