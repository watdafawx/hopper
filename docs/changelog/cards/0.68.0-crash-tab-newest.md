# Crash reports open on the newest report; a report that can't be drawn still opens a card

**Branch:** t3/crash-reports-select-newest   **Commits:** ecbbcbc (desktop), cb8162e (web)   **Size:** S (+ web extra)
**Apps:** both. Desktop instance Logs & crashes and desktop server Logs & crashes (shared `crash_list.rs`), and Hopper Server's web UI (`ServerLogs.svelte`).

## From -> to
- Before (desktop): the report picked on an earlier visit stayed shown when the player came back to Crash reports, and a crash that arrived since never took its place (older "MCEF and Sodium" card under a newer "WebDisplays failed to load" row).
- After (desktop): opening the tab, or its Crash reports sub-tab, shows the newest row (including failed-to-load and stuck-start rows). A click sticks while on the tab. A report that arrives while the tab is open selects itself. Picks are by file name, so a new row above never shifts them.
- Before (web): when a picked report's card failed to draw, the right side stayed empty (the user's WaterFrames report); a failed read showed one bare line; an empty reply left the spinner on.
- After (web): every picked report ends in a card: the reading, or "Hopper couldn't show this report" / "couldn't read this report" with the error, Open report, Try again, Share. A report that arrives after "Look again" selects itself.

## Cause
- Desktop: `crash_list::watch` re-picked only when the shown report was gone from the list, and nothing reset the pick on entering the pane (`LogsView::select` / `show_for`, `ServerLogsView::select` / `show`). Selection was already by file, not index.
- Web: `ServerLogs.svelte` rendered `ServerCrash` with no error boundary. Any exception while drawing it (I forced one with a null suspect) leaves `.read` empty, exactly the report: row selected, right side blank. NOT found: the real data that throws on the user's server. I could not reproduce it from a plausible report + log (the story card for "mod stopped loading, then a knock-on crash" drew fine), so the exact trigger is unknown. The fix makes any such failure visible instead of blank.
- The web sub-tab switch needed no fix: the component remounts, so it already opened on the newest (checked on the old build).

- Tests: `cargo test --bin hopper crash_list`: 5 pass (nothing shown, pick sticks, new crash wins, deleted pick falls back, pick kept by file when a row above goes).
- On screen, desktop: scratch HOPPER_DATA_DIR, throwaway instance "Crashy" with 3 fake crash reports (then a 4th), before and after builds side by side; MCP clicks; all seen in screenshots.
- On screen, web: scratch hopperd 0.57.2 (--data/--home/--servers-root, HOPPERD_SERVICE=hopperd-test, loopback, port 8797), fake server "WF-test" with a mod-loading crash report + log; real browser (T3 preview), old build via embedded UI, new via Vite dev proxy. - NOT checked: desktop *server* Logs & crashes view on screen (same `crash_list` code and the same two edits as the instance view; builds and compiles, not driven); Hopper Server's "Reading the report" with a remote Hopper Server paired to desktop; the exact data from the user's WaterFrames server.
