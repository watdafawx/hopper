# Group sync: a loader version change reaches everyone following the pack

**Branch:** t3/399e7fb5   **Commit:** badb88d (code: 976c78e)   **Size:** M
**Apps:** desktop only. Hopper Server has no group sync of instances (hopperd doesn't use `groupsync`); its pack sync (`server_pack_update`) is a separate path with its own loader handling, so there is no same gap there.

## From -> to
- Before: one member moving NeoForge 21.1.200 -> 21.1.256 re-published the code, but members already following the pack ignored its loader and stayed on the old one.
- After: the loader is one more synced item with the mods' rules. Followers move to the new version by themselves; the task says "Sam updated NeoForge to 21.1.256"; the pack row says "Sam updated the loader".

## Rules (same as mods)
- Two-way, latest change wins (relay seq / stamps); echoes change nothing; a member whose copy is behind undoes nothing; a change made here and not sent yet holds the incoming one back.
- Only the version of the same loader kind is followed. Another kind (NeoForge -> Fabric) is left alone with the note "Alex switched this pack to Fabric. Install it again from their share code to follow."
- A pack's own loader and the same loader named outright are not two states (the code leaves out the pack's own; a merge that finds the loader already here changes nothing).
- Install: the merge saves `inst.loader`, then the store runs `install_loader` (the Settings path, which also tells CurseForge). If the game runs, it waits until the game closes.

## Notes for the maintainer
- Going back to the pack's own loader (Some -> none in the code) sets the instance to its pack's loader, via `make`'s new `pack_loader`.
- There is no History entry for loader changes (a manual change in Settings has none either); the line is in the task's notes and the pack row.
- A change to another loader kind keeps its mark (so a later older change still loses), and the pack row hides it while this instance isn't on that loader.
