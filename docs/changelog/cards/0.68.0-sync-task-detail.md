# Server sync: a detailed task, and Hopper Server downloads public mods itself

**Branch:** t3/detailed-server-sync-progress   **Commit:** fd0fb14   **Size:** L (two asks: detail + server-side download)
**Apps:** both. Desktop: the Tasks row. Hopper Server: new `files.fetch` capability and route `POST /api/v1/fs/{id}/fetch`. Web UI has no sync task (sync is started from desktop), so no Svelte change.

## From -> to
- Before: the sync row said only "Updating <server>" with a bar, every jar was uploaded from the PC (slow on a home upload), and the done row just said it finished.
- After: the row says the step in plain words and "N of M files", a second line shows the current mod's icon + name and "done of total · speed · time left" (the install task's format); each public jar (Modrinth, CurseForge, GitHub link) is downloaded by Hopper Server itself and sha1-checked, falling back to upload if that fails or there is no link; the done row says what changed ("Added X, Y; updated Z; removed W · Hopper Server downloaded 3 files itself, 1 uploaded (3 MB)") and each failed file with its reason.

Mock: https://claude.ai/artifact/VKxNP1WuVNMBrzFe4KXTDD (picked B: two lines, item line under the step line, like installs).

## Timing: same small pack, PC upload capped at 200 KB/s
Pack: AppleSkin 3.0.8 -> 3.0.9, FerriteCore, Jade added, a 3 MB custom jar added, "Old Leftover" removed. Scratch hopperd on loopback behind a throttling proxy (`slowproxy.py`, 200 KB/s PC -> server, counts bytes).

| Panel | Time (click to done) | Bytes uploaded by the PC |
|---|---|---|
| Hopper Server 0.56.0 (no fetch: all uploaded) | 20.8 s | 4.14 MB |
| This branch (server downloads FerriteCore, Jade, AppleSkin) | 17.2 s | 3.20 MB (only the custom jar) |

The saving is the public jars' bytes at the PC's upload speed (here 0.92 MB ≈ 4.6 s at 200 KB/s); a real pack of 300 public jars saves nearly the whole upload. The server's own download from the Modrinth CDN was flaky from FOX (one request hung, the next took 0.6 s).

## Files
- `crates/hopper-core/src/modfetch.rs` (new): mod host allowlist, links for a pack's jars (CF, Modrinth sha1 lookup, GitHub), checked download.
- `crates/hopper-core/src/hosting/files.rs`: `fetch_into`, sha1 + size + path checks.
- `crates/hopperd/src/fs_api.rs`, `api.rs`: fetch route, same access as upload; `files.fetch` cap.
- `crates/hopper-core/src/hopperd.rs`: `fetch_file`; upload progress inside a chunk.
- `crates/hopper-core/src/sync.rs`, `server_update.rs`: fetch-else-upload, steps, file counts, summary.
- `crates/hopper-core/src/words.rs`, `modpack.rs`, `jobs.rs`, `lib.rs`: wording, link data, job item cleared on finish.
- `src/gpui/tasks.rs`: item line at bar indent, numbers never truncated, done text wraps.

## Notes for the maintainer
- Server downloads only https from `edge.forgecdn.net`, `mediafilez.forgecdn.net`, `cdn.modrinth.com`, `github.com`, `objects.githubusercontent.com`, `release-assets.githubusercontent.com`; redirects must stay on that list; size + sha1 must match before the file is moved in; replaced file goes to the trash like an upload. Review `modfetch::allowed`/`fetch` and `fs_api::fetch` closely (new network egress from the panel).
- A hung server-side download waits for the HTTP timeout (~60-120 s) before Hopper falls back to upload.
- Mod name on the task row isn't clickable (no peek host in the title-bar popover).
- The finer upload progress (`ChunkLink::put` reports bytes sent) also applies to every other upload to Hopper Server.
- Old panels (no `files.fetch`) keep the upload path; checked live against 0.56.0.
