# Sync tab: the pack/server comparison does its independent work at the same time

**Branch:** claude/sync-speed-01d150   **Commit:** 4a49045   **Size:** M
**Apps:** desktop only. Hopper Server's web UI Sync page and its `/mods` route already use the cached, threaded scan; `mods_with_off` there gets the off-jar speedup for free.

## From -> to
- Before: opening Sync did the pack scan, Modrinth side lookups (each unknown jar read and sha1'd one by one), the server scan, last-crash read, NeoForge and pack-marker reads strictly one after another.
- After: pack and server sides run together; crash / NeoForge / marker reads run beside the comparison; sha1 of jars and reads of turned-off jars use the shared worker pool. Same diff, same order.

## Numbers (1,200-jar fixture per side, ~150 differences, `--profile local`, OS file cache warm)
| Stage | Before ms | After ms |
|---|---|---|
| scan pack, first run (jar metadata, 16 threads, already existed) | 83 | 83 |
| scan server, first run | 72 | 72 |
| scan either side, cache warm | 1.4 | 1.4 |
| diff_mods | 3.1 | 3.3 |
| pack + server warm, one after other / together | 3.1 | 2.0-2.3 |
| sha1 of 1,200 jars (Modrinth side lookup, unknown-side jars only) | 952 | 170 |
Cold = Hopper's scan cache empty, not a cold disk (needs a reboot to test). Scan and diff were already cheap: the cached, threaded scan was in place. Real gains show where waiting is on disk/network: sha1 of jars with no known side (first open, or new jars), turned-off jars (were opened one by one, uncached), and the rescan waiting on four extra reads (crash scan, config diff, NeoForge, marker; each is an HTTP call for a Hopper Server link, or a share read) before showing anything.
