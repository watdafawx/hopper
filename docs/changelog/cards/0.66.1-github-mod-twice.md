# Updating a GitHub mod no longer leaves it in twice

**Branch:** t3/github-mod-update-duplicate-jars   **Commit:** c6e3b0a   **Size:** M
**Apps:** both. The fix is in hopper-core, so the desktop and Hopper Server (its Mods update route calls `install::apply_updates`) get it together. No UI change.

## From -> to
- Before: if a mod update finished while a group sync, a followed pack or "Sync with friends again" was changing the same instance, the older copy was saved over the update. The new jar stayed in the mods folder with no entry, an older version came back beside it, and History had no row for the file that was replaced. The ATM10 / foxs-tweaks case: two History rows and the mod loaded twice.
- After: jobs that change an instance's mods take turns per instance. An update reads the instance again before it puts files in. Updating a GitHub or link mod also moves leftover unlisted jars of that mod to History. The result is one jar, one entry, and one History row for each update.

## Cause (from the real instance, read-only)
- ATM10 `.hopper-backups`: 13:41:55 (1.22.0 replaced), then 13:42:48 (1.20.0 replaced). In between, `history.json` shows server sync copying `foxstweaks-1.20.0` out of the instance with no 1.23.0 present. So 1.20.0 went back in with no backup row.
- The instance is shared to a group, and a quiet group merge loads the instance at its start and saves at its end. The mod peek's Update button (`src/gpui/browse.rs:3002`) and the Versions dialog (`src/gpui/versions.rs:178`) start an update without the busy check. The update job also worked from the window's possibly older copy.
- Neither job held a lock while it worked, and each saved its own list. The stale writer replaced an entry whose jar the other had already moved, so `backup_into` found nothing and made no History row. Its save also dropped the other job's new jar from the list.

## Notes for the maintainer
- The mod peek's Update button and the Versions dialog still start updates without `edit_hold_reason`. That is safe now, because the core lock makes the update wait. Left as is: adding the check would be a UI behaviour change.
- The real ATM10 instance now has a single `foxstweaks-1.23.0` jar, so there is nothing to clean up. It also has other flip-flops from the same race: botany 0.5.2, vista 5.6.5, and crazyphone beta.6 from another member's code.
- `edit_lock` is separate from `update_on_disk`'s `root_lock`, so quick changes from the window never wait for a long job.
