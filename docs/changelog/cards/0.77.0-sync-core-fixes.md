# Friends group sync: a member's undo isn't lost, locked mods stay, failing updates stop retrying

**Branch:** t3/fix-group-sync-logic-gaps   **Commit:** fc05c0c   **Size:** M
**Apps:** desktop logic only (hopper-core). Hopper Server has no friends sync. No UI changed.

## From -> to
- Before: a member's undo of the sharer's change was lost if the member sent another change before the sharer came back; the two copies stayed different for good, silently.
- After: the sharer takes the undo too (sync scenario gap 1 passes).
- Before: a group change could update, remove or put back the file of a mod the player had locked.
- After: a locked mod keeps its file (on/off still syncs); the merge result lists what was kept and why.
- Before: a group update that always fails was retried every 15 seconds forever.
- After: after 10 quick tries Hopper stops trying that code by itself and says so once; internet / mod site / held-file failures keep trying every 5 minutes. A newer code is tried at once.

## Notes for the maintainer
- API for the UI agent: `groupsync::Merged::kept: Vec<Kept>`; `Kept { key, name, kind, by, why: KeptWhy::Locked }` with `Kept::says()` ("Sodium stays as it is: you locked its version. Mia changed its version."); `groupsync::locked_out(&Instance, &Change) -> bool`; `recipe::Retry::gave_up: bool`; `recipe::GIVE_UP_AFTER` (10), `recipe::SLOW_RETRY` (5 min). `on_group_merged` doesn't show `merged.kept` yet.
- The existing failure notice in `friends.rs` already reads right when Hopper stops (no "tries again" because `next` is `None`; `tell` is set once on stopping). It needs a "Try again" for a given-up code (drop its `group_retry` / `follow_retry` entry).
- The retry cap is in `recipe::Retry`, so it covers plain follows too, not only group copies.
- A locked mod's skipped change is taken in (not retried). Unlocking later doesn't bring that change back; the next change of that mod does.
- Lock means `Addon::locked` only; `locked_version` (one skipped update of a link mod) isn't checked by group sync.
